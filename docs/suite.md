## Start Center

One card, in its own colours and in Google Sans Flex (`fonts/brand.css`). It does not follow a look, does not load `looks.css`, and has no Settings, Themes, Update, Install or cache notice. No title bar of its own (installed, the window has the system's). It opens centred: the mark and the name, then Ecrivaine, Matheuse and Oratrice (each a blank document), then Open, New File from Template and Recent Files. A file dropped on the page, picked with Open, or passed by the operating system (installed app, `launchQueue`) goes to the app for its extension (`VO.appFor`); other files get a message above the footer.

On a wide window (wider than 700px), **New File from Template** (`#templates`; the old `#create` is the same) and **Recent Files** (`#recent`) move that same group to the left. The right side reuses the template gallery (Documents, Spreadsheets and Presentations, Blank then each app's templates) or the Recent Files cards (thumbnail, name, app, when, a remove button; an unsaved card is marked and can open the saved version). The address is replaced, so Back does not return there; the mark and the name do, and that replaces the address again. **About** (`#about`) is another view in the card; Back returns to the arrangement it was opened from.

On a narrow window the card shows only the centred group. Templates, Recent Files and About each take the card, with Back and a title, the same way, and Back returns to that centred home. The three do not stack on each other.

The footer stays on every view: the language (a menu of language names; the browser's language is used only while the stored choice is still Auto, and choosing a name stores that language and uses it from then on), then MIT License, Feedback on GitHub, OSS Software Licenses and About. A look is chosen in an app (Help ▸ Theme, or Tools ▸ Options ▸ General ▸ Theme). Per-app settings stay in each app's Tools ▸ Options.

Installed (display mode standalone) or in the desktop app, app pages open in a new window and the Start Center stays, as in LibreOffice (`VO.host.newWindow`); in a browser tab they open in the same tab (Back returns).

## Windows

No page draws a title bar of its own: the browser tab, or the system title bar of the installed app, shows `document.title` (`<document> - Ecrivaine`). Each app sets its own icon as the page icon with `VO.setIcon(L.icons.app(32))`.

## The host: `VO.host`

What runs the pages: a browser, the desktop app (`desktop/`, Tauri), or a VS Code / code-server custom editor (`vscode/`). `VO.host.kind` is `web`, `desktop` or `vscode`. On the VS Code host, `documentPath` and `documentDir` are the open file and its folder. `HasHostAbility` and the audit tiers are in [docs/dom_api_security.md](dom_api_security.md). `platform`, `version`, `onFiles(fn)` (the PWA's `launchQueue`, or the desktop app's command line; the Start Center hands them to their app), `openUrl(url)`, `newWindow(url)` / `closeWindow()` and `uiScale()` / `setUiScale(n)` (`null` on the web and in VS Code, where the browser's own zoom does it). Pages use `VO.host` for anything the hosts differ in. The desktop side is in docs/desktop.md (Host interface). The editor side is in docs/vscode.md: it opens the workspace file the custom editor was given (`VO.launch` is `{ vscode: true }`, a blank document, then that file) and `L.saveFile` writes it back through `VO.host.writeFile`. File ▸ New and File ▸ Open there use VS Code's own dialogs and open the file in a new tab (`createDocument`, `openWorkspace`). New File… creates a blank `.docx`, `.xlsx` or `.pptx` in the workspace and opens it; the page keeps its own blank document and writes that into the file (`adoptBlank`).

## App launch: `VO.launch` and `VO.attach`

| URL | The app starts with |
|---|---|
| `<app>/` | a blank document (`Document1`, `Book1`, `Presentation1`) |
| `<app>/?new` | a blank document (`Document1`, `Book1`, `Presentation1`) |
| `<app>/?template=<id>` | a new document from that template (`Document1`, `TaskTracker1`, `Presentation1`) |
| `<app>/?open=<id>` | a blank document, then the file the Start Center stored under `id` in the `handoff` store (read once, then deleted; entries older than a day are swept) |
| `<app>/?recent=<key>` | a blank document, then that Recent Files entry |

The query is removed from the address once read, so a reload starts clean. Opening the file replaces the untouched blank document (each app already does this for its own File ▸ Open), so it ends up in one window.

File ▸ Exit closes the app's documents (asking to save each; Cancel stays) and calls `VO.exit()`: an app window the Start Center opened (installed) closes, showing the Start Center behind it; a tab goes to the Start Center.

Each app, in its `A.init`, picks a template or a blank document from `VO.launch` and finishes with

    VO.attach('<app>', { open(file, { draft, name, saved }), thumb(), message(text), templates(),
                         snapshot(doc), docInfo(doc), isDirty(doc), current(), autosave(), showRecovery() })

and reports `VO.opened(file, doc)` after any successful open (File ▸ Open, drop, Start Center), `VO.saved(name, blob, doc)` after a save in its own format, `VO.changed(doc)` after an edit and `VO.discard(doc)` when the user drops the changes (Ecrivaine `.docx/.dotx`; Matheuse everything but web pages and PDF; Oratrice `.pptx/.ppsx/.potx`). Every call is guarded with `if (window.VO)`, so an app page still runs on its own.

The New toolbar button still makes a blank document straight away, as in Office.

Placeholder text says what goes where (Ecrivaine's are click-to-replace fields). The gallery's list and pictures are generated, never edited by hand: after adding or changing a template run

    node tools/templates.mjs

which opens every app and template in Chromium and writes `public/common/templates.json` and `public/<app>/templates/<id>.jpg` (`blank.jpg` for Blank). That Chromium is for the pages in a browser. A VS Code extension change does not start it; the user checks the extension in VS Code. On WSL2, do not look for Chromium on Windows or on the WSL2 host, and do not run commands outside the workspace (AGENTS.md).

What each app provides:

- before `core.js`: `<script>window.L = { APP_ID: 'ecrivaine', APP_NAME: 'Ecrivaine', APP: 'Ecrivaine' };</script>`. `APP_ID` prefixes the app's settings in localStorage (`ecrivaine.…`), so it must never change.
- in its `app.js`, at load: `L.icons.app` (its icon), `ui.hooks = { beforeExec, refocus, commitEdit }` (its editor around commands, toolbar boxes and dialogs); Oratrice also `ui.schemeColors` / `ui.currentDesign` (theme colours in colour menus) and PowerPoint's `L.SIZE_LIST`.
- a spelling UI sets `L.spell.refreshSoon` if it draws underlines (Ecrivaine).

**Drags.** Every press-and-drag of the apps (moving a shape, a ruler marker, a cell range, drawing a shape, a
splitter) is a `ui.drag(e, { move, up, cancel, threshold, capture })` from `ui.js`: one at a time; `move` only after
4 px, so a click that never moved changes nothing; `up` on the release; `cancel(d, why)` instead, with nothing
committed, on Esc (which also ends the tool and puts a brush down), Ctrl+Z or Ctrl+Y (the drag is what gets undone), a
second button (its menu doesn't open), a release the page never saw, a lost capture, the window losing focus or
`ui.dragCancel()` (a tool, view, sheet, slide or zoom switch); a tool stays armed after the other cancels. Other keys
go nowhere while the button is held (the modifiers still shape the drag), and each app's history push (Ecrivaine `D.tx`,
Matheuse `O.tx`, Oratrice `L.hist.push`) cancels a live drag before it records, so no edit comes between a drag's start
and its step. The cursor of the press stays while the pointer moves (`cursor: false` holds none). The browser's own
text-selection drags stay its own; Ecrivaine watches its text selections with a `ui.drag` that holds nothing
(`{ capture: false, cursor: false }`), so a selection let go in another window or cut short by Esc or a second button
ends without `'sel-done'` (`tests/ui/drag.test.mjs`, `tests/ui/gestures.test.mjs`; todos/UI_MOUSE_LOGIC_IMPROVE.md).

**Selections.** Each app has one setter for its selection, and it ends the other kinds: Ecrivaine's `E.setSel` ends an
object selection (`E.selectObject` is the one way into one, `E.clearObjSel` the one way out), Matheuse's `G.select`,
`G.selectRange` and `G.selectAll` end a drawing object's, Oratrice's `E.select` ends text editing and a range of table
cells. Oratrice's `E.endInteraction()` ends what is under way on the slide (a drag, a freeform, a cell range) on a tool
switch, another slide and undo.

**Focus.** The keyboard stays with the document unless the user picks a control of its own. A press on chrome with
none (a toolbar's, the ribbon's or a pane's background, a grip, the status bar, a tab strip), on a menu, the menu bar
or a button outside a dialog keeps it where it is (one `mousedown` listener in `ui.js`). A dialog closing gives it back
to what had it, editable text with the selection it had (Oratrice's speaker notes), except the document's own text
(`ui.hooks.ownsText(el)`: Ecrivaine's page, Oratrice's slide), which the app's `ui.hooks.refocus()` gives back with its
model selection (Ecrivaine `E.refocus`, Oratrice the text at `L.te.lastSel`, the slide or the Slides pane); a menu command
that leaves it nowhere calls `refocus()` too (`tests/ui/focus.test.mjs`).

**Dialogs.** Opening one leaves the windows already open where they are. The new one comes to the front, stepped down
and to the right so the one behind stays in view, and a click on a window behind brings that one forward when no modal
dialog is in front of it. A modal dialog puts a veil behind every open window (transparent in the Windows 7 and Windows XP looks) and
keeps the windows behind it from taking clicks; a modeless one (Find and Replace, Cross-reference, Mark Index Entry,
the Watch Window, Error Checking) does not. `canClose: false` leaves off the title's close button, and Escape does not close that window (it does not press Cancel either; a button the user clicks still runs). `resizeable` defaults to false. When it is true, dragging an edge or a corner changes the window's size. The title bar does not gain a button for that. `minWidth` and `minHeight` are the smallest size, and `onResize` runs as the size changes. `restoreWindowSizeAndPosition` defaults to 0. Set to 1, the window's left, top, width and height are kept for this app and used the next time it opens. `windowName` is that stored name; without it the title is the name. While work keeps the user waiting, `ui.busy` opens that same modal: the title is the app's name, there is no close button and no buttons, and a window already open (including the one shown while a file is opening) stays up underneath it. Windows 7 and Windows XP draw it as they draw any modal. The front modal is the active window; a modeless window is active only while it holds the keyboard, and inactive once focus leaves it (a click in the document). Inactive windows fade the title and the text; the Windows 7 look instead softens the frame, drops the glass blur from 4px to 2px and leaves the close button as the glyph alone. A press outside the front modal (on the veil, the document or a window behind it) flashes that modal between the active and inactive looks six times, 80 ms each, then leaves it active. A popup menu or a right-click menu is always drawn above every window and above the formatting bar. The formatting bar is drawn above every window. A button that opens a further dialog (Customize on Bullets and Numbering,
Special on Go To, Replace on Oratrice's Find, Chart Options on Format Chart) leaves the first window open.

**Zoom.** Each status bar ends in a zoom control (`ui.zoomBar`): minus, a slider and plus, and a percent that can be typed. On a window up to 960px wide the cells to the left of it are hidden and a Document Status button opens them, one to a line, in a modeless window 100px wide; the zoom control stays. Dragging the slider or a settled number changes the document at once (Ecrivaine 10–500%, Matheuse and Oratrice 10–400%). 100% is the middle of the slider: the left half runs from the minimum to 100%, and the right half from 100% to the maximum (`ui.zoomTrack`). A pinch, or Ctrl+scroll, over the editing area zooms the document about the pointer; two-finger scrolling moves it (`ui.watchDocGestures`). The same pinch on the menus, toolbars, ribbon or status bar does not zoom the page. The slider's groove and thumb follow the Windows slider (`.references/7.css`, MIT), in the look's own colours.

**Brushes.** The Format Painter of each app, and Ecrivaine's highlighter, is a `ui.brush({ el, pick, apply, hint, status })`: a click on its button arms it for one use or puts it down, a double-click keeps it on, Esc puts it down, and one brush is on at a time. Arming it changes nothing else: the selection and the text being edited stay. It paints once, when the mouse is let go, never while a selection is still being dragged out: the app calls `brush.release()` then (Ecrivaine on the editor's `sel-done`, Matheuse at the end of a cell drag, Oratrice at pointer up in the slide editor) and its `apply` paints what was marked. What the apps paint follows Office and LibreOffice's Clone Formatting (Writer, Calc, Impress): a click inside a word paints the word; Matheuse tiles the source range over a larger target; Oratrice carries the text's formatting from text being edited and the whole object's otherwise, paints the text dragged over in any box and the whole object when the press is beside its text, and a click beside the objects puts even a kept-on painter down. The painted formatting replaces the target's own; links, fields and revision marks stay (`tests/ui/painter.test.mjs`).

Version: `VO.VERSION` in `suite.js` is the one version string (`L.VERSION` reads it); it says `dev` in the repository, the desktop app's build sets it, and the published copy stamps it. The format is `v<yyyy>.<mm>.<dd>-<6 hex>`, the date (UTC) and commit of the tree (`tools/current-tree-version.sh`, e.g. `v2026.10.11-d2134d`; copies before said `2026.10.8f8494`). `VO.compareVersions(a, b)` compares two by their dates alone (negative, 0, positive; `dev` is newer than any dated version, an old-format one counts as day 0 of its month). The Start Center's About shows it. Each app's Help ▸ About shows `public/version.json` instead, as `Version: v<version> (<commit>), Build Date: <date>` (half-width colons, not translated; `tools/package_vsix.sh` writes the file when it packs the VS Code extension). `public/updater/current.json` names, per policy and platform, the oldest version that needs no Update button or dialog, and `public/updater/whatsnew.json` what each version brought, for the Update dialog (docs/desktop.md, Versions and updates).

## Looks

The chrome (menus, toolbars, task panes, dialogs, status bar, rulers, sheet headers) can be drawn in more than one look: **Classic 7** (glass buttons and dialogs; the menu bar is the Windows 7 gradient, and menus, including right-click menus, are the Windows 7 menu), **Classic XP** (Luna windows, menus and controls, on the classic blue toolbars), **Classic** (Office 2003 blue throughout) and **Ribbon 2010** (the same ribbon, drawn as the Office 2010 silver bar with a blue File tab and gold buttons; the windows, buttons, scroll bars and type are a copy of Windows 7) and **Golden Gate** (the default; that ribbon on a macOS window: a white toolbar, gray plates under the colourful icons, liquid-glass tabs, menus and group pop-ups, and a close button and a centred title; the open and close motion is Windows 7's, copied under its own name) and **Golden Gate (Dark)** (that same window and ribbon, with Puppertino's dark colours only: `#1E1E1E` chrome, white-opacity type, and `#0091FF`; the page around the paper, the area around a slide, and the side bars go dark, while the paper, the sheet and the slide stay light) and **Golden Gate (Follow VS Code Color Theme)** (a separate copy of that window, listed only inside VS Code and code-server: the window follows the editor background, the ribbon tab bar follows the title bar, where the menu bar is drawn, and the controls follow the theme's button, menu, list and input colours; the liquid glass follows whether that theme is light or dark). The user picks one in Help ▸ Theme (a mark on the current look; the File menu has the same list when the ribbon is showing), or in Tools ▸ Options ▸ General ▸ Theme of any app. The Start Center does not offer it and does not draw itself in the chosen look. It applies to the whole suite and every open window at once. Golden Gate is the choice when none has been stored. In a VS Code or code-server webview that choice is Golden Gate (Follow VS Code Color Theme). A stored choice of Paper or Paper 2016 opens as that same default, and that choice is what is stored from then on. Golden Gate, Golden Gate (Dark) and Golden Gate (Follow VS Code Color Theme) are listed first, then Ribbon 2010. Classic 7, Classic XP and Classic (and the separator before them) stay in `LOOKS` with `hidden: true`, so Help ▸ Theme and Options ▸ Theme do not show them.

- `common/looks.css` holds every chrome colour, font and shadow as a named setting (`--chrome-line`, `--pane-ink`, `--btn-a`, `--hdr-sel-a`, …), one block per look keyed by `data-look="…"` (on `<html>`, or on any element to preview a look inside another); Classic's block is also `:root`, so a page with no look set still has colours. Paper adds a few shape rules a colour cannot express (rounded trays, pill tabs), scoped `:is([data-look="paper"], [data-look="paper2016"])`; Paper 2016 shares Paper's block and adds nothing of its own but the layout. Ribbon 2010 copies the Windows 7 block under its own `data-look` (the Windows 7 rules stay as they are) and then restates the ribbon: silver tab strip `#eaedf1`, white selected tab, blue File tab (a vertical blue gradient, with a lower-middle glow from two half-width highlights clipped by the tab; hover is lighter, pressed is dark along the top) and gold buttons (hover `#fdf9e8` through `#fde38a` to `#fdfdeb`, edge `#f1ca58`; pressed `#f3c25f` to `#fddd81` with an inset shadow, edge `#c2762b`; a button that stays selected is the flat Office 2010 hover, `#fdeeb3`, edge `#F1C43F`), fading with the Windows 7 toolbar timing (1s, 250ms while pressed). The rulers use that same gray. Lists that open from the ribbon (the font list, the colour grid and the other pickers) use Paper 2016's rounded menu, filled with that gray, the current row in flat gold (`#fdeeb3`, edge `#F1C43F`), and the hovered row in the same gold glass as a ribbon button. The File menu and right-click menus stay the Windows 7 menu. Its type is the copied Windows 7 face and 11px. Windows 7 adds the glass shapes (toolbar buttons, dialog frames, the formatting bar after a text selection, the default button's blue edge). Its menu bar uses the Windows 7 gradient (white to pale blue, blue highlight), and its menus, including right-click menus, use the Windows 7 menu (gray face, gutter, blue hover). Tooltips and the assistant's speech balloon use the Windows 7 balloon face and shadow (white to gray); only the speech balloon has the tail. Windows XP keeps Classic's blue toolbars, task pane, read and preview bars, minibar and floating bar, and Classic's sheet headers, rulers, selection and canvas. Its menu bar and menus are the Luna menu (`#e8e6d6`, highlight `rgb(64, 102, 196)`), its windows are the Luna frame (active and inactive title from paint-xp, the six-layer border from XP.css, caption buttons from XP.css's images), and its buttons, fields, tabs, scroll bars and status bar are XP.css. Tooltips and the speech balloon stay the Windows 7 balloon. `ui.css` and each app's CSS use only these settings for chrome. The Start Center uses colours of its own.
- Only chrome is themed. Document content (pages, cells, slides, comments, revisions, objects and their handles, Excel's in-cell buttons), icons and colour swatches keep their colours in every look. The page and the slide sit on `--page-canvas` inside a one-pixel `--page-line`. Selected document text, and a selected range of cells, take a translucent gray (`--text-sel`, `--cell-sel`) that leaves the text's own colour in place.
- Each app page's head sets `data-look` from `localStorage['melinaoffice.look']` (default `goldengate`, or `vscodegg` when `window.__VO_HOST__.kind` is `'vscode'`) and `data-layout` (`ribbon` for Ribbon 2010, Golden Gate, Golden Gate (Dark) and Golden Gate (Follow VS Code Color Theme), otherwise `bars`) on `<html>` before the stylesheets load, so a page never flashes the wrong look. ## The assistant: Nikki

Nikki (暖暖) is the suite's assistant, and the place where an AI assistant will live later; for now she offers a few things to do. She is in every app, in every look, and comes in when an app starts, except on iOS and Android (`L.isMobile` in `core.js`) and in an automated browser (`navigator.webdriver`: Playwright, and `tools/shot.mjs`, which says so), where she comes in only once the user has shown her. Hiding her lasts the day: she doesn't come in by herself again until the next day.

- **Help ▸ Show the Assistant** (`showAssistant`, defined by `assistant.js`; it reads *Hide the Assistant* while she is shown) brings her in at the bottom right with a wave (Greeting), nothing said, except the first time she is shown each day (from the menu, or when an app starts with her): then she waves, says good morning, afternoon or evening by the clock, introduces herself and asks what the user would like to do: *Good morning! I'm Nikki. I'll keep you company while you work. What would you like to do?*, with choices: Find a command by name (points at Search commands and puts the cursor in it), Look something up in Help, Get started, See the keyboard shortcuts (each only where the app has that command), Send me a wink, Nothing for now. Coming in by herself once she has greeted today (another app, the next start), she just pops in (Show), with nothing to say. A click on her asks *What would you like to do?* with the same choices (or closes the balloon); she can be dragged anywhere. A click leaves the keyboard focus in the document.

An app starts with her when it isn't the day she was hidden and either the user last showed her or the platform has her by default. Showing or hiding her in one window does so in the others (the `storage` event). A stored `id` of `scout` is treated as Nikki.

## Preservation

Same-format Office saves carry what the model cannot edit. These contracts apply to all three apps;
the current feature and edit-behaviour tables are in [Ecrivaine](ecrivaine.md#what-a-save-keeps-converts-and-drops),
[Matheuse](matheuse.md#what-a-save-keeps-converts-and-drops) and
[Oratrice](oratrice.md#what-a-save-keeps-converts-and-drops). Conversions to Markdown, CSV, PDF and other
formats have their own rules.

- OOXML preservation uses `common/opc.js`: immutable package bytes stay outside JSON history; model fragments carry source identities and dependency references. Classify parts as opaque, merged or regenerated. Preserve original identities unless every referrer is regenerated; duplicates remap definitions and references together. Merge settings-like parts only; regenerate content parts with model-attached fragments. Record conversions and drops in the document's loss matheuse.
- Save and drafts keep the main-part variant and encryption. Save As changes the filename/type only after a successful download. Show the unacknowledged entries marked `notify` in the Compatibility Checker after preparing the file and before download (see [What the user is told](#what-the-user-is-told)); acknowledge only a successful user save. Drafts neither show nor acknowledge the checker. Recompute writer losses on every save so cancelling a conversion does not poison the next save.
- Preserved content-control boundaries and binding updates participate in undo. Keep boundaries balanced through edits and paste, remap copied identities together, and roll back the whole transaction when a content/deletion lock forbids it. Typed value commands retain their binding; ordinary typing that converts a typed control records that conversion.
- Retained formatting belongs to individual properties: compare the owning model fields, replace only the property the user changed, and keep its siblings. Capture property alternatives before normalisation and emit changed children in Office-compatible schema order. Copy range endpoints together with fresh identities; report incomplete ranges at save.
- Rewritten parts hoist repeated namespace declarations. Keep a minimal local `mc:Ignorable` list when a scoped `PreserveAttributes`, `PreserveElements` or `ProcessContent` rule requires it; moving that processing rule to root would widen its scope.
- Opaque frames belong to their displayed objects. A compatibility wrapper with several model members is emitted once only while all members remain intact, ordered and contiguous; never resurrect deleted content. Geometry updates preserve the payload. Clipboard transfer includes preview bytes, dependent parts and implicit references, with copied definitions and references remapped together.
- Preservation changes are measured against the pinned corpus (`tools/corpora.sh`), including edits, undo/redo and drafts. Record failed and excluded attempts, compare validator diagnostics with each original, and keep Office acceptance pending until it has actually been checked. The measurement tools are in `tools/ooxml/`.

| Part ownership | Writer contract |
|---|---|
| Opaque | Carry original bytes and original relationships; follow their dependency graph, including cycles and shared targets |
| Merged | Start with the original settings-like part and replace only model-owned properties in schema order |
| Regenerated | Write model content and attached fragments; preserve identities used by any retained referrer |

Strict inputs save as Transitional OOXML with a recorded conversion entry (not shown: Office reads both alike). This explicitly
converts retained XML namespaces and vocabulary; binary dependencies remain unchanged. It preserves
the document/template/slideshow and macro variant.

`L.opc.open` reads the immutable baseline; `attach` keeps it out of JSON snapshots. `fragment` records
namespace context, relationship attributes and identity definitions/references. `captureAC` runs on
the original XML before branch selection, and `emit` writes an outer compatibility record once.
Inherited compatibility attributes are merged by namespace URI and local name, even when an ancestor
and a fragment use different prefixes. Repeated saves must not add a second `Ignorable` attribute
under an alias; the fragment keeps its own spelling and the inherited value list.
Fragments stay self-contained in history and clipboard data. Once a regenerated or merged part is
assembled, `output.put` hoists missing namespace declarations and the union of `mc:Ignorable` onto
its root. It removes redundant inner declarations, keeps actual prefix rebindings and default-namespace
resets, and leaves other compatibility properties scoped as written. Opaque parts bypass this pass
and keep their bytes. This prevents every preserved paragraph/run property from repeating the full
document namespace list.
`patch` assembles disjoint source slices once, so namespace cleanup does not copy a large part
for every removed declaration. Insertions at shared boundaries retain their original order.
`duplicate` assigns a shared copy identity to the selected definitions and references; `export` and
`import` transport their dependency bytes between documents. The writer reserves existing part names,
relationship IDs and identity spaces before allocating new values. Master and layout IDs share one
space; non-empty preset adjustment lists include every preset value in Office's order.

GUID-bearing models opt into `duplicate` with `guidAttributes` and `guidFields`. Supply `guidValues`
to identify definitions explicitly when some fields refer to shared people or other shared objects.
`guidSources` includes definitions in separately written XML parts; `guidMap` receives their shared,
JSON-safe mapping. Copies allocate these IDs during the edit, so undo, drafts and repeat saves keep
the same IDs. `remapGuids` applies that mapping when the app writes a dependent part. It changes
identity attributes only: relationship IDs, text, URLs and extension URIs keep their own meaning.

The loss matheuse distinguishes conversion from deletion and keeps stable entry identities. Specific
object conversion/deletion notices can account for their opaque dependency trees with `coverLoss`;
this suppresses redundant part notices without removing any parts or crossing rewritten-content
boundaries. Unexplained missing parts still produce their own loss entries. Digital
signatures are removed and reported because a changed package cannot retain their validity. Missing
dependencies and unavoidable conversions are reported by the writer; draft recovery retains pending
entries even when the original content has already been converted in the draft.
`output` runs its app-owned audit after assembling content. `reportFeatures` compares specified
features in regenerated parts, so retained wrappers do not warn merely because the reader uses a
simpler model. Chart/drawing regeneration and notes-page formatting conversion report at their
writer branches. Cancelling a conversion and then saving the original representation clears its
save-time notice; only a completed download acknowledges current notices.

### What the user is told

Every entry is recorded (corpus drivers and tests read `doc.losses`), but the Compatibility Checker
shows only entries with `notify: true`: the user loses content or a working feature. That covers an
object removed, SmartArt/OLE/ink saved as shapes or a picture, a slicer, control, comment thread or
media that stops working, macros or a signature removed, pivot cells Office will overwrite, and parts
of a damaged file that could not be read. Silent: repairs of damaged or invalid input that keep the
content, format normalisation (Strict to Transitional, pre-release markup), formatting details behind
an edit the user made, objects the original already lacked a part for (`L.opc.sourceMissing`), and
audit catch-alls. The unreferenced-part and `reportFeatures` entries are bug alarms for corpus runs:
a real loss should get its own notice where it happens.

Shown entries are plain sentences about the user's content ("This IntelliArt will be saved as ordinary
shapes, because it was edited here."), with `place` in the user's terms (a sheet, cell, slide or
control name). Part names and error text go in `where` and `detail`, never in the dialog. The dialog
groups identical messages and lists their places.

An Office review batch contains at most 15 files and a checklist. Before handoff, compare the new save
with the previous writer's save of the same input and explain each difference. Automated validators
and LibreOffice do not establish Office acceptance. Keep run history outside the repository in
`~/corpora/results/<run>/README.md`, and keep app docs focused on current behavior and measurements.

## Recent Files and unsaved versions

One list for everything a user worked on, shown in four places: the Start Center (cards), each app's File menu (1–4), its Getting Started pane (Open) and its Document Recovery pane. Every entry really reopens.

IndexedDB database `melinaoffice`, store `recent`: `{ key, app, name, size, time, file, thumb, draft }`, keyed `<app>:<file name>`, or `<app>:~<id>` for a document that was never saved. The browser has no file paths, so the list keeps a **copy of the file**: `file` is the one opened or last saved; `draft` (`{ file, name, time, lossState }`) is the **unsaved version**. Two files with the same name in different folders share an entry. At most 30 entries, but an entry with unsaved changes is never dropped; files over 50 MB are not kept. Every page hears about changes over the `BroadcastChannel` `melinaoffice` (`VO.onRecentChange`); `VO.recent.cache` is the list for menus.

**Keeping the data.** Safari clears a site's data after about 7 days without a visit; the first time a document's unsaved version is stored, `navigator.storage.persist()` asks the browser to keep it (Safari and Chrome decide without asking the user). Where IndexedDB is missing (Safari's Lockdown Mode), the Start Center shows an alert explaining how to turn Lockdown Mode off for the site.

**Autosave.** The app calls `VO.changed(doc)` when a document changes; 15 s later (longer for documents that are slow to write: 30 × the time the last write took) `hooks.snapshot(doc)` writes it in the app's own format (including macro, template and slideshow variants; password-protected documents stay encrypted) into the entry's `draft`. `VO.opened(file, doc)` and `VO.saved(name, blob, doc)` tie the document to its entry; saving clears the draft (and retires the `~` entry of a never-saved document); No in "Do you want to save the changes…?" calls `VO.discard(doc)`, which throws the draft away. Closing the tab or a crash leaves it. Draft metadata also keeps pending and acknowledged compatibility entries; recovery restores them silently so the next user save can report an earlier conversion. Ecrivaine's Tools ▸ Options ▸ Save ▸ "Save AutoRecover info" turns it off.

**Recovery.** When an app starts and other documents of it have unsaved versions, it opens the **Document Recovery** task pane (as in Office 2003): each one with *Open the unsaved version* and *Discard the changes*. Opening one (`VO.openRecent(key, { draft: true })`, or `<app>/?recent=<key>&draft` from the Start Center) restores the changes as unsaved, so the document still has to be saved; a never-saved one then asks for a name. On the Start Center such a card is marked *Unsaved changes* (or *Never saved*), opens the unsaved version, offers *Saved version* when there is one, and × discards the changes.

Thumbnails are JPEG, at most 320 px, made 0.6 s after an open, a save or an autosave of the current document from `hooks.thumb()`: Ecrivaine rasterizes its first page as for PDF (print layout only), Matheuse crops the top left of its grid canvas (4:3, at most 600 px wide), Oratrice draws slide 1. Without one, the card shows the app's page picture and the extension.

## PWA

The manifest's `id`, `start_url` and `scope` are `./`, so the suite installs from any folder it is served from. Shortcuts create a new document, spreadsheet or presentation (`<app>/?new`). File handlers (`.docx .dotx .docm .rtf .md .markdown`, `.xlsx .xltx .xlsm .csv`, `.pptx .ppsx .potx`) all go to the Start Center, which hands the file on; `launch_handler` `focus-existing` reuses an open Start Center window. App pages link the same manifest, so installing from inside an app installs the suite.

Icons: edit `public/icons/icon.svg` and `icon-maskable.svg` (no SVG filters: Safari rasterises those at CSS pixels), then:

    tools/rebuild_icons.sh

That writes the PWA PNGs (`icon-192.png`, `icon-512.png`, `icon-maskable-512.png`, `apple-touch-icon.png`) and the desktop mark (`desktop/icons/icon.png`, `icon.ico`, `icon.icns`) plus each app's document `.ico`. Needs `rsvg-convert` and ImageMagick, not Chromium.

## Service worker

`public/sw.js` caches the published site for offline use. It works only under https://acane.net/melinaoffice/ (not the rest of that host) and on 127.0.0.1 (any port, to try a published copy locally: docs/testing.md): `common/suite.js` registers it there (the worker's scope is the directory of `sw.js`, so `/melinaoffice/` on the published site; `updateViaCache: 'none'`, so the browser always asks the server for `sw.js`) and removes any earlier registration anywhere else (localhost, preview deployments). On the dev server (`tools/serve.py`, 127.0.0.1:8760) the files are unstamped (`VERSION = 'dev'`), so the worker is registered but caches nothing and answers no request: local work never meets a cache. The desktop app has none.

**Publishing.** First the whole UI suite, `node tools/ui-full.mjs` (docs/testing.md); both scripts below warn when it has not passed on this `public/` (`tools/ui-tested.sh`). `../cf-melinaoffice/sync-cf-pages.sh` copies `public/` and runs `tools/web-release.sh <copy> <version>`, which stamps the version (`tools/current-tree-version.sh`) into the copy's `common/suite.js` and `sw.js` and packs `updater/web-<version>.zip` (Info-ZIP `zip`): every file but `sw.js`, `updater/` and hidden files, about 4.4 MB for the 10.5 MB site. The changed `sw.js` is what makes browsers install the new worker. In the repository `VERSION` stays `'dev'`, and an unstamped worker caches nothing.

**Install.** The worker downloads the version's zip, the whole site in one file (so one consistent version, whatever the server does meanwhile), and unpacks it into the cache `melinaoffice-<version>` with the apps' own ZIP engine (`importScripts('common/zip.js')`: the browser's inflate where there is one, its JavaScript inflater otherwise), each file checked against the size and CRC-32 in the zip's central directory and given the `Content-Type` of its extension. The whole site is cached, the dictionaries too, so spelling works offline; every update downloads the whole zip again. Anything failing (offline, a download shorter than its `Content-Length`, a damaged zip or one the reader had to repair, a name the site can't have, storage full) fails the install: the half-filled cache goes, the earlier worker goes on serving, and the browser tries again on a later visit. Old caches are deleted only after the new worker has activated, never during install: until then the earlier worker still serves the open pages from its cache.

**One version per page.** Each page is served from the cache of the version it was loaded with (the cache `melinaoffice-clients` records page → version), so an app page open while an update lands goes on loading scripts of its own version, never a mix (the apps load 20–45 classic scripts that must match). Navigations get the newest version. So the new worker takes over at once (`skipWaiting`, `clients.claim`) with no "reload to update" prompt: each page updates the next time it loads. An old version's cache goes once no open page uses it, checked on activation and on each navigation, and never while a newer worker is still installing.

**Answering requests.** GET requests for the site's own files come from the cache, offline too, whatever their query (`?new`, `?template=`); a folder is its `index.html`, and a folder without its slash (`/ecrivaine`) is redirected to it. `updater/` (the update check, the zips), `sw.js`, other methods and anything not in the zip go to the network; a navigation to a page not in the zip that the network can't answer goes to the Start Center.

**Progress.** While it installs, the worker posts `{ type: 'vo-cache', state: 'progress', update, progress, received, total, version }` to every page of the site (progress: the download up to 0.8, then the unpacking; received and total: the zip's bytes, total 0 if the server didn't say), then `{ state: 'failed', error }`, or `{ state: 'done', update }` once the new worker has taken over (from its activation, so a reload is answered by the new version). `common/suite.js` turns these into a `vo-cache` event on `window`. The Start Center does not show a progress bar or a reload notice; an open page keeps its version until it is loaded again.

`node --test tests/sw.test.mjs` checks all of this on staged copies (docs/testing.md).
